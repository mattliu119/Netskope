AI Agent 治理：9 大控管面向的 Netskope 落地 AI Agent Governance: Nine Control Domains with Netskope

從盤點、身分、執行期防護到稽核營運，讓 AI Agent 像數位員工一樣可管、可控、可追溯 From discovery and identity to runtime protection and audit, govern AI agents like digital employees

AICC 先找出所有 AI 應用與 Shadow AI；GenAI 應用由 CASB Inline 管控，AI Agent 的工具呼叫由 Agent Action Control（原 Agentic Broker）控制與檢查；呼叫 Claude 與地端 LLM 的 API 流量（例如在 PowerShell 執行的 Claude Code）則獨立經過 AI Gateway，以 AI Guardrail（CPU-based）與 DLPoD 在地端檢查。CASB API 巡檢 Skill 庫，所有活動集中記錄於 SkopeIT。 AICC first finds every AI app, including shadow AI. API traffic to Claude and on-prem LLMs (for example Claude Code run from PowerShell) takes a separate path through the AI Gateway, checked on-prem by AI Guardrail (CPU-based) and DLPoD. CASB API scans the skill repository, and every activity is logged in SkopeIT.

02 · Human-in-the-Loop Tiers

Agent 動作風險分級與人類介入Agent Action Risk Tiers & Human Involvement建議範例Suggested example

依 Agent 動作的風險決定人類介入程度：低風險由人在旁監看（HOTL），中高風險需要人確認或直接阻擋（HITL）。Human involvement follows the risk of the agent's action: low risk is watched from the side (HOTL); medium and high risk need a human decision or are blocked (HITL).

Tier 風險Risk Agent 動作Agent action 對應活動 / MCP 工具呼叫Activities / MCP tool calls 政策動作Policy action 人類介入Human role
Tier 1 低Low 查詢、搜尋Query, search Browse · Response · List_files · Search Allow HOTL · 記錄監看logged & watched
Tier 2 中Medium 上傳、貼文、建立 / 更新Upload, post, create / update Upload · Post · Create_file · Update_record User Alert HITL · 使用者自行填寫理由後放行user self-justifies to proceed
Tier 3 高High 分享、連接外部服務Share, connect external services Share · Connect · Merge_pull_request Block HITL · 需經人工核可（外部流程）needs human approval (external process)
Tier 4 嚴重Critical 刪除、大量操作Delete, bulk operations Delete · Delete_repo Block + Alert 阻擋並通知管理員blocked, admin notified

此分級為建議範例，並非 Netskope 內建分類。Netskope 依活動或工具呼叫套用 Allow／User Alert／Block；Tier 的劃分與對應動作須依組織的風險容忍度定義。This tiering is a suggested example, not a built-in Netskope classification. Netskope applies Allow / User Alert / Block per activity or tool call; how tiers are drawn and which actions they map to depend on the organization's risk appetite.

Tier 3 的人工核可需搭配外部流程（如工單、主管核准後調整政策）；User Alert 為使用者自行填寫理由後放行，不是由他人審核。因此 6-1、6-2 標示為部分支援，實際分級需與客戶討論後定案。Tier 3 approval needs an external process (such as a ticket, with the policy adjusted after a manager approves); User Alert lets users justify and proceed themselves rather than being reviewed by someone else. That is why 6-1 and 6-2 are marked partial, and the final tiering should be agreed with the customer.

03 · Key Design

關鍵設計Key Design

三條流量，各有控制點Three paths, three control points

使用者用 GenAI 走 CASB Inline；AI Agent 呼叫工具走 Agent Action Control；應用以 API 呼叫 Claude 或地端 LLM 則獨立走 AI Gateway，由 AI Guardrail（CPU-based）與 DLPoD 在地端檢查，資料不必送出企業。CASB API 再無代理巡檢 Skill 庫，補上落地後的檢查。GenAI use goes through CASB Inline; agent tool calls go through Agent Action Control; API calls to Claude or on-prem LLMs take a separate path through the AI Gateway, checked on-prem by AI Guardrail (CPU-based) and DLPoD without sending data out. CASB API scans the skill repository agentlessly to cover what lands later.

發現 → 評估 → 核可 → 監控Discover → assess → approve → monitor

由 AICC 自動發現所有 AI 應用、Agent 與 Shadow AI，以 CCI 與 MCP Server 風險分數評估。低風險自動核准、高風險送資安委員會審批；上架後以即時政策管控並持續監控，未核可的 Agent 直接阻擋。AICC discovers every AI app, agent and shadow AI automatically, scored with CCI and MCP server risk. Low risk is auto-approved, high risk goes to the security committee; once onboarded, real-time policy and monitoring apply, and unapproved agents are blocked.

提示詞即程式碼Prompt as code

Skill 與 Agent 設定檔集中在單一來源（如 OneDrive），禁止私設工具庫。檔案落地前經 Netskope 掃描，確保沒有機敏金鑰殘留，審核結果可串接 Teams 通知，不拖慢開發。Skills and agent configs live in one source of truth (e.g. OneDrive) with no private tool libraries. Netskope scans files as they land to make sure no secrets are left behind, and review results can flow to Teams without slowing developers.
